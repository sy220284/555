# 全量并行执行模型

## 从第一天存在的设计骨架

4基础体系、15国数据骨架、5级科技、16张多人图、24个战役任务、核心建筑/单位/能力槽位和三种**规则深度预设**一次建立。它们可以同时处于不同实现生命周期，不代表第一天就具有正式资产或可玩代码。

## 统一生命周期

所有系统/内容统一使用：

`design_defined -> data_defined -> code_contract_ready -> placeholder -> playable -> validated -> content_complete -> ship_ready`

不得再用含义模糊的“基本完成”“差不多”“已接线”等词代替生命周期状态。

失败态作为工作流标签叠加：`blocked / test_failed / performance_regression / needs_refactor`，不能替代生命周期。

## 动态优先级

P0：阻塞编译、权威数据、确定性、安全或主线；P1：核心可玩性闭环；P2：完整系统；P3：内容生产；P4：表现打磨。总控AI根据阻塞关系动态调整，不按固定月份串行推进。

当前风险驱动顺序以 `09_FULL_DESIGN_IMPLEMENTATION_AUDIT.md` 与 `IMPLEMENTATION_TEST_GATES.md` 为准。

## 模块所有权

同一核心模块同时最多2—4个编码代理，避免热区冲突；地图、战役、配置、测试等可以高并发，但必须共享统一Schema/生成器/验证器，禁止每个内容任务复制一套实现。

## 接口优先

核心功能第一交付应包含：输入、输出、权威状态、事件、错误语义、稳定ID、测试契约。下游在接口稳定后可使用明确标记的占位实现并行开发。

接口存在只允许标 `code_contract_ready`，不能标 `playable`。

## 主线要求

### G11之前：实现启动期

主分支至少必须保持：

- 权威数据验证通过；
- 已纳入Unity的代码不故意破坏编译契约；
- 生命周期与实际状态一致；
- 每个新增核心规则都有数据/代码/测试中的下一落点；
- 不批量生产依赖尚未验证规则的大量正式资产。

### G11之后：可玩主线期

第一局完整歼灭灰盒达到 `playable` 后，主分支必须持续保持：

- Unity批处理编译通过；
- 基础对局可从开始走到胜负；
- 无画面模拟和状态哈希可运行；
- 核心自动测试通过。

此后大重构必须通过兼容层/迁移逐步替换，禁止主线长期不可玩。

## 交付闭环

任何对象的“完成”必须对应明确生命周期，并具备相应代码/数据、测试、集成、确定性、性能、文档、AI使用/反制和资产许可。未满足的部分必须如实留在下一状态。

## 人工保留的最终权限

产品裁决（是否好玩）、创意裁决（是否符合世界/阵营）、视觉裁决、法务/授权裁决、发布裁决。编码、数据生成、回归、统计、平衡模拟、文档一致性尽量自动化，但自动化结果仍必须通过对应门禁。
