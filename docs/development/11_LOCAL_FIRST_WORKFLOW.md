# 本地优先开发工作流

本文件定义 555 项目的强制开发路径。适用于代码、数据、工具、工作流、测试和实现型文档修改。

## 1. 唯一允许的开发顺序

所有实现修改必须按以下顺序推进：

`权威文件校准 -> 本地工作空间修改 -> 本地测试/复核 -> 本地 Git 提交 -> 远端分支/PR -> 远端门禁 -> 合并 main -> main 再验证`

禁止把 GitHub 远端分支当作试错工作区。禁止先在远端修改，再补本地验证说明。

## 2. 本地工作空间

默认工作空间：`/mnt/data/555-workspace`。

若运行环境不同，可以使用其他本地路径，但 PR 必须记录实际路径。临时生成物、测试夹具、缓存和工具输出不得误提交为权威仓库内容。

## 3. 本地完成定义

允许提交远端前，当前批次至少满足：

1. 修改内容已经全部写入本地工作区；
2. 与当前任务直接相关的本地单元/静态/无画面测试已经执行；
3. 能执行的语法、格式、结构、数据一致性检查已经通过；
4. 已检查 `git diff` 和 `git status`，确认没有无关文件；
5. 已形成一个可追踪的本地 Git 提交；
6. 已记录本地测试命令和结果；
7. 无法在本地执行的门禁必须明确标为外部门禁，不得伪造通过。

## 4. PR 必备本地证据

每个实现 PR 正文必须包含以下三个字段，字段内容不得为空：

- `本地工作区：` 实际本地路径；
- `本地提交：` 本地 Git 提交短哈希或完整哈希；
- `本地测试：` 实际执行的命令与结果摘要。

推荐同时记录：

- 本地发现并修复的问题；
- 本地未能执行的外部门禁；
- 与主线权威规则是否存在变更。

## 5. 远端职责

GitHub 只承担：

- 保存已经在本地闭环的提交；
- PR 差异审查；
- Linux/.NET/Python 等持续集成复核；
- Unity 自托管、目标硬件等本地环境无法替代的最终门禁；
- 合并与 main 回归。

远端门禁失败后，修复必须回到本地工作空间完成，再提交新的本地提交；禁止直接在远端网页编辑器试错。

## 6. 外部阻断

缺少 Unity 编辑器、许可证、自托管执行器、目标硬件或其他外部条件时：

1. 保持对应门禁 `PENDING/BLOCKED`；
2. 把可以提前完成的静态校验、诊断、测试契约和产物捕获在本地实现；
3. 不允许用模拟日志、手工 YAML、伪造锁文件或口头说明替代真实门禁；
4. 外部条件恢复后直接运行既有门禁，不重新设计一套流程。

## 7. 合并后闭环

PR 合并不等于任务完成。必须再次检查 `main` 对应持续集成结果。只有 main 回归通过，当前批次才可标记完成。

## 8. 禁止事项

- 禁止远端先改、本地后补；
- 禁止没有本地提交号的实现 PR；
- 禁止只写“测试通过”而不写实际命令/结果；
- 禁止把无法运行的 Unity/性能/硬件门禁写成通过；
- 禁止将本地测试夹具、缓存、生成目录误提交；
- 禁止为绕过本地失败而直接修改 CI 期待值。

本流程属于开发硬规则；与个人操作习惯冲突时，以本流程为准。
