# 在线服务、匹配、排位与运营技术规格

本文件冻结游戏服务器以外的在线服务边界。权威战斗服务器仍以 `development/03_NETWORK_DETERMINISM.md` 为准。

## 1. 总体拓扑

```text
客户端
→ API Gateway / Auth Adapter
→ Account/Profile Service
→ Party/Lobby Service
→ Matchmaking Service
→ Session Allocator
→ Dedicated Game Server
→ Result Service
→ Rating/Leaderboard
→ Telemetry/Event Pipeline
```

推荐后台：Go；事务数据：PostgreSQL；会话/临时队列：Valkey/Redis类缓存；大规模遥测分析：ClickHouse。

## 2. 服务边界

### Account/Profile

保存：平台账号映射、显示资料、设置云备份（如启用）、封禁状态、区域偏好、隐私同意版本。

不得保存游戏账号密码明文；优先使用平台登录或标准授权协议。

### Party/Lobby

负责：组队、邀请、房间成员、准备状态、规则集、地图/模组哈希、队伍分配。

### Matchmaking

输入：模式、区域、队伍规模、排位分、延迟、平台池、输入设备策略、版本、内容哈希。

输出：匹配票据和候选会话，不直接决定战斗结果。

### Session Allocator

选择可用 Dedicated Server 节点，签发短期会话凭据，把地图、规则集、种子、双方名单和内容哈希发送给服务器。

### Result Service

只接受权威服务器签名结果。客户端提交的胜负、击杀或资源统计不能直接改排位数据。

## 3. 排位分

首发采用隐藏匹配分 + 可见段位。

隐藏分：团队模式按队伍预期胜率更新，考虑预组队修正；不得按击杀数直接加减隐藏分，防止刷数据破坏胜负目标。

可见段位建议：

`青铜 -> 白银 -> 黄金 -> 白金 -> 钻石 -> 大师 -> 统帅`

每个大段可分3个小段；大师以上采用积分榜。

赛季软重置只压缩分布，不完全清零历史能力估计。

## 4. 匹配目标

优先级：

1. 版本/规则集完全兼容；
2. 队伍规模兼容；
3. 区域延迟；
4. 匹配分公平；
5. 预组队强度；
6. 等待时间。

搜索随等待时间逐步放宽分差，但排位默认不跨超过设定最大延迟阈值。

参考延迟目标：

- 理想：<=60ms；
- 可接受：<=100ms；
- 超过150ms默认不进入排位自动匹配，除非区域人口不足且玩家选择扩大范围。

## 5. 地图池与选图

排位地图池按赛季配置。

1v1可采用服务器随机+近期重复规避；高段位可提供双方各1次地图禁选。

团队模式避免复杂实时BP拖长匹配，默认从认证地图池按队伍规模随机，并对最近3场重复图降权。

地图/规则配置必须版本化并写入比赛记录。

## 6. 掉线、重连与弃赛

- 断线保留60秒重连窗口；
- 短时断线由L1防守接管，不允许战略进攻；
- 玩家主动退出后仍允许在窗口内恢复；
- 多次故意弃赛进入逐级冷却队列；
- 服务器故障无法恢复权威状态时结果为 `NO_CONTEST`，不处罚玩家。

处罚必须区分客户端崩溃、网络中断、服务器故障与明确主动弃赛。

## 7. 投降

规则以 `specs/GAME_MODE_RULES.md` 为准。后台记录投降类型、时间、队伍投票，但不把正常投降本身视为违规。

## 8. 赛季与排行榜

每个赛季记录：

`season_id, start_at, end_at, ruleset_version, map_pool_version, balance_version`

排行榜至少提供：全球、区域、1v1、团队。隐私设置允许玩家隐藏部分公开历史，但竞技排名本身可保持公开显示名。

## 9. 赛事模式

赛事房支持：

- 固定地图/规则；
- 裁判槽位；
- 延迟全图观战；
- 服务器区域锁定；
- 比赛暂停权限（仅赛事）；
- 权威录像自动归档；
- 赛后结果签名导出。

普通排位不开放任意暂停。

## 10. 遥测事件

统一事件信封：

`event_id, event_version, match_id, player_pseudonymous_id, timestamp, game_version, map_id, ruleset_id, payload`

高频战斗细节先由服务器/客户端聚合再上传，禁止把每发子弹作为后台事件。

关键事件：比赛开始/结束、重连、崩溃、投降、科技选择、单位产量、经济曲线、战略能力、AI授权、性能摘要。

## 11. 数据留存

- 排位结果/处罚/版本：长期保存；
- 详细权威录像：按成本和政策分层留存；
- 调试级高频遥测：短期留存并聚合；
- 玩家隐私数据遵守地区法规和删除请求；
- 分析系统优先使用假名化玩家ID。

具体安全与隐私以 `ONLINE_SECURITY_PRIVACY.md` 为准。

## 12. 发布与兼容窗口

客户端和服务器必须携带：`game_version, protocol_version, content_hash, ruleset_version`。

匹配只连接兼容版本。

热修复顺序：

1. 部署新后台/服务器兼容版本；
2. 小比例节点验证；
3. 扩大服务器池；
4. 发布客户端/内容更新；
5. 旧版本进入只允许完成现有对局的宽限窗口；
6. 宽限结束后停止新匹配。

禁止“客户端先更新、服务器后兼容”的不可控发布。

## 13. 灰度与回滚

所有在线服务必须支持：

- 按区域/比例灰度；
- 版本健康指标；
- 一键停止新会话分配；
- 回滚到前一稳定镜像；
- 数据库向前兼容迁移或可逆迁移方案；
- 规则/地图/平衡配置版本回滚。

## 14. 可观测性

至少监控：登录成功率、匹配耗时、取消率、分差、服务器分配失败、游戏服崩溃、重连成功率、结果上报失败、地区延迟、协议不兼容、作弊拒绝、后台P95/P99延迟。

## 15. 验收

必须覆盖：1v1/团队匹配、组队、跨区域延迟限制、版本不兼容、服务器容量不足、分配后服务器崩溃、结果重复上报幂等、重连、弃赛处罚、NO_CONTEST、赛季切换、地图池更新、灰度和回滚。
